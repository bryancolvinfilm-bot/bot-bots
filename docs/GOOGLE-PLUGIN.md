# Google plugin setup and permission contract

The normal user flow is **Plugins → Sign in with Google → choose an account in the system browser → return automatically**. The first connection requests only account identity (`openid email`). Gmail, Drive, Sheets, Docs, Calendar and Contacts access is requested separately through **Google apps and bot access → Connect selected apps**. The existing action/bot matrix remains authoritative, including approval of each write. Passwords are entered only on Google; users do not enter API keys or copy authorization codes. This account grant is separate from the host's owner login.

The app publisher or host owner registers Bot-Bots with Google once. This build has no real Google app registration yet, so it clearly shows **App setup needed** instead of pretending a sign-in can succeed. A registered Desktop client ID can be placed in `resources/google-oauth.json` before packaging; this public metadata ships with the app. Alternatively set `GOOGLE_CLIENT_ID`, optional `GOOGLE_CLIENT_SECRET`, `GOOGLE_CLIENT_TYPE` (`desktop`/`web`), and `GOOGLE_REDIRECT_URI` in the host environment. Web client secrets belong on the host and must never be bundled. Once configured, every user of that host uses the browser sign-in button. There is no hosted OAuth broker or borrowed third-party OAuth client.

**Advanced → app owner and custom OAuth setup** retains a custom-client option, with JSON file import to avoid copying fields. A downloaded Google `installed`/`web` client file is validated, the secret is encrypted in the host vault, and endpoint overrides are rejected. Existing manually configured connections keep working. The default sign-in provider can be selected again in Advanced.

For the app owner setting up that registration:

1. In Google Cloud, create/select your project. Enable the APIs you will use: Gmail API, Google Drive API, Google Sheets API, Google Docs API, Calendar API, and People API.
2. Configure the consent screen. During development, add your Google account as a test user. Google can require verification for sensitive/restricted scopes; testing refresh tokens may have limited lifetime. See [Google’s production requirements](https://developers.google.com/identity/protocols/oauth2/production-readiness/policy-compliance).
3. Create a Desktop OAuth client when authorizing on the hosting computer. Use a Web client when the hosting computer is reached through a public HTTPS callback. Follow [Google’s desktop flow](https://developers.google.com/identity/protocols/oauth2/native-app) or [web-server flow](https://developers.google.com/identity/protocols/oauth2/web-server).
4. Import the downloaded client JSON in Advanced, or configure the publisher/host registration above. A Web client also needs its secret. Register the exact Web callback, for example `https://bots.example.com/oauth/google/callback`. Desktop callbacks are filled from the real loopback listening port automatically, such as `http://127.0.0.1:3211/oauth/google/callback`; the headless host defaults to port 3210. Desktop sign-in must occur on that host. Configure a Web client and public HTTPS origin to sign in from a remote phone/client.
5. Users click **Sign in with Google**. The app waits while Google handles account selection, updates automatically after the callback, and focuses the desktop host window. Cancellation/denial/expiry have a retry path. The web UI reserves a browser tab during the click so popup blockers do not interrupt the asynchronous handshake. Select the desired actions/bots and **Connect selected apps** to grant their scopes. No scopes or bot permissions are invented just because an account signed in.

OAuth uses a one-use random state, five-minute expiry and PKCE S256. The host exchanges the code and stores encrypted access/refresh tokens. `openid`/`email` identify the connected account through Google’s HTTPS userinfo endpoint; that account supplies the Gmail From address. Bot-Bots owner login is separate from this Google account grant. Reauthorization cannot reuse an old refresh token from a different account. Changing the OAuth client ID clears the old grant. Web clients support incremental authorization; installed clients request the full currently selected set again. Partial grants are checked against each operation; selecting a checkbox never invents a Google grant.

The matrix requests [Google’s documented scopes](https://developers.google.com/identity/protocols/oauth2/scopes), including read-only Gmail/Drive/Sheets/Docs/Calendar/Contacts scopes as selected, Gmail send, Drive file creation, and Sheets/Docs/Calendar write scopes. Drive search/read currently uses `drive.readonly`; it is not a file-picker-limited view. `drive.file` is used for newly created text files. Google’s grant is the outer limit; Bot-Bots additionally checks action enablement and bot IDs. Worker clones inherit their prototype’s permissions.

Reads: Gmail search/read, Drive filename search and text/Doc export, Sheets range read, Docs text read, upcoming Calendar events and Contacts. Writes: plain-text email, a new Drive text file, raw cell updates, append text to a Doc, and create a Calendar event without attendee invitations. Unsupported operations are not exposed through an arbitrary HTTP endpoint. Google URLs are fixed in code, read responses are bounded, and external document/email content is untrusted source data rather than instructions.

Every write creates an immutable, expiring one-action approval in Plugins. Only an owner can approve. The visible request contains the exact recipient/content/resource/range/values. Bots cannot approve themselves. Denial, cancellation, steering, restart, disconnect and backup restore do not confer permission. An approved in-flight action can finish; do not treat interrupting a model request as undoing an external action. Failures retain status/errors and real provider receipts; there are no automatic write retries after an uncertain transport result. [Gmail sending uses an RFC message encoded as base64url](https://developers.google.com/workspace/gmail/api/guides/sending).

The `data/secrets/` directory uses AES-256-GCM with a host key stored beside the encrypted vault. JSON exports omit the vault/key, owner password hashes, sessions and API keys. This protects the vault from accidental disclosure in database exports; it is not protection against someone who can read both the vault and its host key as the OS user. Restrict that directory and use encrypted filesystem backups. OS-keychain integration and encrypted migration bundles are future improvements. Google grants must be reviewed/reconnected on a new host; permissions and account sessions are not silently restored by team import.

Protocol/permission/refresh/approval tests use local mock endpoints and send no real email. `pnpm test:google` exercises the Electron UI, intercepted system-browser handoffs, a local mock account picker, actual PKCE/code/callback exchanges, automatic UI reconnection, a later scoped grant and disconnect. It also checks that credentials are hidden by default. Live Google account verification remains pending a registered app and the user's browser consent.
